Legacy Modernisation

Replace it without stopping work

Somebody built a Microsoft Access database years ago. It runs job cards, pricing and half the invoicing. One person understands it, and she retires in March. It sits on a tower under a desk that nobody dares restart, because the last reboot broke the reports for a week. The business depends on it completely, and not a single page of documentation exists anywhere.

Onva Labs handles legacy system migration while the work carries on. First we write down what the old system actually does, including the undocumented habits people have built around its quirks. Then we rebuild it in stages. Legacy software modernisation is mostly data migration, which means moving years of records into a new structure without losing, duplicating or mangling them along the way.

Working out what it really does

Before anything is rebuilt, we trace the screens, the reports and the spreadsheets people quietly keep alongside, because undocumented behaviour is where rewrites usually come undone.

Replacing Microsoft Access databases

Unsupported PHP and old frameworks

Desktop apps nobody can install

Software that only runs on one ageing machine, moved to the browser so new staff can use it without hunting for an installer and a licence key.

Strangler fig instead of big bang

Application modernisation named after the vine: new parts grow around the old system, taking over one function at a time until the original can be switched off.

Database migration services done carefully

Mapping old fields to new ones, cleaning decades of inconsistent entry, then running repeated test loads you verify before a single record moves for real.

Why businesses trust this approach

Staged legacy system migration means you are never one failed cutover away from a standstill. Each piece goes live on its own, and the old system stays available until it is genuinely redundant.

Old versions stop receiving security patches, which quietly raises your risk. Where the system holds personal information, the Privacy Act 1988 and the Notifiable Data Breaches scheme make that a board-level concern.

Everything gets documented as we go, so the new system is not another thing only one person understands. Handover notes are part of the work, not an optional extra.

Data is reconciled rather than assumed correct. Record counts, financial totals and manual spot checks are compared against the old system before anyone agrees that a migration is finished.

Common questions

Why not rewrite the whole thing at once?

Because big-bang rewrites fail in a predictable way. The old system keeps changing while the new one is built, nobody remembers every edge case, and the launch date becomes a cliff. Staged replacement avoids that: one function moves at a time, each goes live on its own, and you can pause the programme without being left stranded between two systems.

Our old system still works. Why change it?

Working is not the same as safe. The usual triggers for replacing legacy software are a person retiring, software versions that no longer receive security patches, hardware that cannot be replaced, or an inability to connect the system to anything newer. If none of those apply and the risk is understood, waiting is a legitimate decision, and we will say so.

How much of the project is data migration?

Most of it, more often than people expect. Years of inconsistent entry, duplicated records, free-text fields holding three different things and rules that live in someone's memory all have to be untangled. We run test migrations repeatedly, reconcile counts and totals against the original, and only move live data once you have checked the result.
